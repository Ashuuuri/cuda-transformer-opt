對 INT8 優化來說

兩者結構幾乎一樣：GEMM → 非線性 → GEMM

INT8 加速策略一致：
  • 兩個 GEMM 用 INT8 tensor core（可達 624 TOPS）
  • 中間的 softmax / GELU 必須在 FP16 下做（exp / tanh 不能 INT8）
  • 所以在兩個 GEMM 之間需要 dequant → 算 → requant
這就是你的 int8_attention.cu 和 int8_mlp.cu 在做的事。
🛠 INT8 實作流程（目前進度）
顏色規則： INT8（1 byte 整數）· INT32（4 byte 整數，GEMM 累加用）· FP16（2 byte 浮點，softmax / GELU 用）

核心規則：GEMM 用 INT8 tensor core 算，中間非線性（softmax / GELU）必須 FP16 → 所以要在兩個 GEMM 之間 dequant → 算 → requant。

每一版的改動細節

v1 — Naive 初版 (baseline, correctness only)
目標：先跑通，驗證資料流對不對。
做了什麼：
  • quant_utils.cu：per-tensor symmetric quantize/dequantize
  • int8_gemm_naive：一個 thread 算一個輸出元素，scalar INT8×INT8→INT32 累加
  • 5 個獨立 kernel 串起來：GEMM → dequant+GELU → quant → GEMM → dequant
  • 每次 forward 都 cudaMalloc 暫存 buffer、結束時 cudaFree
  • 中間 scale 用 cudaMemcpy 拿回 CPU
缺點：
  • 沒用 tensor core（0.1% utilization）
  • 沒 tiling（每個乘法都讀 HBM）
  • 每 forward 4-5 次 cudaMalloc，CPU-GPU sync 斷 pipeline
結果：Attn 1.808 ms、MLP 2.554 ms（比 FP16 慢 17-31×）
v2 — Static Workspace Cache (Step 1：消除 cudaMalloc 開銷)
目標：把 cudaMalloc/Free 從 hot path 移出。
做了什麼：
  • 新增 struct MlpWorkspace / AttnWorkspace，static 全域實例 g_mlp_ws / g_attn_ws
  • ensure(hidden_n, out_n) 方法：首次呼叫才 alloc，之後 reuse；遇到更大 shape 才 realloc
  • 把 forward 裡的 cudaMalloc / cudaFree 全部拿掉，改用 workspace pointer
  • kernel 邏輯完全沒動，只換 buffer 管理
影響：
  • Attention 每 forward 省掉 5 次 malloc+5 次 free ≈ 300 μs
  • MLP 省掉 4 次 malloc+4 次 free ≈ 240 μs
  • CPU 同步點減少，GPU pipeline 不被打斷
結果：Attn 1.104 ms（-39%）、MLP 2.284 ms（-11%）
MLP 收益比 Attn 小，是因為 MLP 的 GEMM 本身就很重，malloc 佔比相對小。
v3 — WMMA Tensor Core + Device-side Scale (Step 1.5 + Step 2)
目標：啟動 INT8 tensor core，拿掉最後的 D2H sync 點。
Step 1.5：scale 全程留 GPU
  • 拿掉 cudaMemcpy(&scale_hidden, g_mlp_ws.d_scale, ...)（每次 forward 的 D2H sync）
  • 新寫 dequant_kernel_dev_mlp / dequant_kernel_dev_attn，接受 const float* scale_A_ptr（device pointer）
  • kernel 內部自己算 scale = (*scale_A_ptr) × scale_B
  • GPU pipeline 完全不被 CPU 打斷
Step 2：WMMA INT8 Tensor Core
  • 改用 nvcuda::wmma API，tile shape 16×16×16（INT8 A→INT32 C）
  • 三個 GEMM 全部換掉：
    • int8_gemm_wmma（MLP 用，row_major × row_major）
    • int8_qk_wmma（attention QK^T，關鍵技巧：B 用 col_major fragment + leading_dim=D，達成 K^T 而不實際轉置記憶體）
    • int8_av_wmma（attention attn·V，row_major × row_major）
  • 執行模型：一個 warp（32 thread）一個 16×16 tile，mma_sync 一條指令算 4096 次乘加
  • Grid 配置：Attention 16K blocks、MLP GEMM1 8K blocks，占滿 SM
解掉的小 bug：
  • 原本 dequant_kernel_dev 在兩個檔案同名，linker 撞名 → 改加 static 並改名為 _mlp / _attn
影響：
  • GEMM 吞吐量從「1 次乘加 / cycle / thread」→「4096 次乘加 / 指令 / warp」
  • 硬體從 CUDA core 轉移到 tensor core，INT8 peak 從 ~20 TOPS → 624 TOPS（理論）
  • 實際 utilization 從 0.3% → 2.1%（還差很多，因為瓶頸轉到 HBM）
結果：Attn 0.216 ms（v2 再 -80%）、MLP 0.336 ms（v2 再 -85%）
累計 v1 → v3：Attention 快 8.4×，MLP 快 7.6×。
v4 / v4.1 — Shared-Memory Tiling ❌ 失敗實驗（已 revert）
目標：block 內 4 warp 共用 __shared__ 的 A/B tile，減少 HBM 存取。
實際數據：
版本 Attention MLP vs v3
v3（baseline）0.216 ms0.336 ms—
v4（smem tiling BM=BN=32）0.284 ms0.420 ms慢 25-31%
v4.1（+ PAD=16 破 bank conflict）0.299 ms0.447 ms慢 33-38%
為什麼反而變慢（事後分析）
  • L2 cache 已經在幫忙：A100 有 40 MB L2，而我們的 working set 很小（Q/K/V 各 ~1 MB，W1/W2 各 ~1 MB），整個 model 全塞得進 L2。v3 從 HBM 讀的 cost 實際上是 L2 hit（~200 cycle，不是 400 cycle）。
  • smem tiling 反而是多餘開銷：
    • HBM → smem 的顯式 copy 多一趟搬運
    • __syncthreads() × 2 per K-tile 的等待
    • Block 變大（128 threads），per-SM 能跑的 block 數減少 → occupancy 降
    • smem load 的 indirection 額外指令
  • Padding 也救不回來：雖然消除了 bank conflict，但載入更多資料（48 byte/row 而非 32），反而稍微更慢。
學到的教訓：
Shared-memory tiling 是「working set 不 fit L2」時的標準優化。但當資料小到 L2 容得下時，顯式 smem 反而無謂地競爭相同的 memory subsystem。

判斷準則：先看 working set ÷ L2 size。
  • > 1 → tiling 有大幫助
  • < 0.1 → tiling 反而慢（我們在這）
  • 中間 → 實測
決定：revert 回 v3，跳過 Step 3，直接做 Step 4 kernel fusion。
v5（規劃中）— Kernel Fusion (Step 4，跳過 Step 3)
目標：把 GEMM + dequant + activation + requant 合成一個 kernel，徹底消除中間 HBM round-trip。
現在 MLP 有 5 個 kernel + 4 次中間 HBM 
GEMM1 → HBM(8MB) → dequant → HBM(4MB) → GELU → HBM(4MB) → quant → HBM(2MB) → GEMM2 → HBM(1MB) → dequant → HBM(1MB)
Fused 版本 
GEMM1 tile → register → GELU → register → quant → GEMM2 tile → HBM(只出最後一次)
實作挑戰
  • GEMM1 的 output tile 必須在 register/smem 裡直接接 GELU（不寫 HBM）
  • GEMM2 的 input 直接從同一 block 的 GEMM1 output 拿
  • Quantize 步驟的「找 max」需要 row-level reduction，要在 block 內做
預期：MLP 0.336 ms → ~150 μs、Attention 0.216 ms → ~100 μs（接近 FP16 baseline）

② 你現在的 thread 配置（naive GEMM）

以 int8_gemm_naive 為例：一個 16×16 的 thread block，每個 thread 算一個輸出元素。

Thread block (16 × 16 = 256 threads)
橘色 T0 負責算 out[0, 0]，其他 255 個 thread 各自算一個元素
每個 thread 的工作： 
for (k = 0; k < K; k++) {
    acc += A[row, k] × B[k, col]   ← 從 HBM 讀 A 和 B
}
out[row, col] = acc                ← 寫回 HBM
問題：
• 每個 thread 的 K 次迴圈裡，A 和 B 每次都要 從 HBM 讀（400 cycles）
• 同 block 的 256 個 thread 讀到的 A、B 有大量重複（同 row 的 thread 共用 A，同 col 的 thread 共用 B）
• 但他們沒有「共享」這些資料 → 一樣的資料從 HBM 讀了 256 次
• 完全沒用到 shared memory 和 tensor core

④ 每次 forward 的 cudaMalloc 開銷

你的 MLP 和 attention forward 每次都做： 

void int8_mlp_forward(...) {
    cudaMalloc(&hidden_int32, 8MB);     ← ~30 μs (同步呼叫)
    cudaMalloc(&hidden_fp16, 4MB);      ← ~30 μs
    cudaMalloc(&hidden_int8, 2MB);      ← ~30 μs
    cudaMalloc(&out_int32, 1MB);        ← ~30 μs

    // ... 真正的計算 ...

    cudaFree(hidden_int32);             ← ~30 μs × 4
    cudaFree(hidden_fp16);
    cudaFree(hidden_int8);
    cudaFree(out_int32);
}
估算：
• 每個 cudaMalloc / cudaFree 約 30 μs（同步、要 OS 介入）
• 每次 forward 有 4+4 = 8 次 → ~240 μs / forward 純 malloc 開銷
• 你的 forward 總共 2554 μs，malloc 吃掉 10-20%（實際上因為 malloc 會 block GPU，影響更大）
• benchmark 跑 50 iter = 12 ms 純 malloc 等待

⑤ Tensor Core 完全閒置

❌ 你現在（CUDA core 做 scalar 乘加）
  • 一個 thread 算一個輸出元素
  • 每次只做 1 個 INT8 × INT8 → INT32
  • 用的是普通 CUDA core（6912 個）
  • 吞吐量：INT8 約 20 TOPS（非常低）
  • A100 的 tensor core 完全閒置 😴
✅ 用 wmma tensor core 會這樣
  • 32 個 thread（一個 warp）協作
  • 一條 mma.sync 算 16×16×32 = 8192 次乘加
  • 用的是專門的 tensor core（432 個）
  • 吞吐量：INT8 可達 624 TOPS
  • 理論快 30 倍以上
A100 的 INT8 tensor core 峰值是 CUDA core 做 INT8 的 30 倍以上。
你現在 utilization 只有 0.1-0.3%，主要就是因為 tensor core 完全沒啟動。

① int8_gemm_naive — 核心 GEMM（你會跑最多次的運算）

這個 kernel 被呼叫 4 次：attention 的 QK^T、attention 的 attn·V、MLP 的 x·W1、MLP 的 hidden·W2。 每個 thread 負責算一個輸出元素（out[row, col]）。

    int32_t acc = 0; ← 放在 register

    1 byte (INT8)
    ~400 cycles latency
    HBM B[k, col]
    1 byte (INT8)
    ~400 cycles latency

    CUDA core ALU

    IMAD 指令，1 cycle
    →
    去向
    Register acc
    累加結果
    ~1 cycle
  4. 迴圈結束，寫回結果
    來源
    Register acc（最終值）
    →
    store instruction
    ST.E.B32
    →
    去向
    HBM out[row, col]

⚠️ 核心低效問題：資料重複讀

一個 block 有 16×16 = 256 個 thread，每個算一個元素。考慮同一 row 的 16 個 thread：
  • Thread T(0, 0), T(0, 1), ..., T(0, 15) 都需要讀 A[0, k] 給 k = 0..K-1
  • 這 16 個 thread 各自從 HBM 讀 A[0, k]，雖然資料完全一樣
  • 同一份 A 被 HBM 傳輸了 16 次
同理，B 矩陣的每一欄會被讀 16 次。
正確做法：一個 thread 讀一份進 shared memory，所有 thread 從 shared memory 共用（只有 20 cycles 延遲，而非 400）。你現在沒做這個。

② dequant_softmax_kernel — attention 的 softmax（3 pass reduction）

每個 block 負責一個「row」（對應 QK 的一行，共 512 個元素）。Block 內 256 個 thread 協作，做 3 次掃過這 512 個元素。

  1. Pass 1: 找 row max
    每個 thread
    HBM 讀 row 中自己負責的元素 (INT32)
    row_in[j], j = tid, tid+256, ...
    ALU × combined_scale
    → float
    取 local max
    整個 block
    Shared Memory tree reduction：
    256 個 local max → 1 個 row max
  2. Pass 2: 計算 exp(v - max)，存 row_out，累加 sum
    每個 thread
    HBM 又讀一次 row_in[j]
    SFU expf(v − row_max)
    Special Function Unit（不是一般 ALU）
    去向
    HBM 寫 row_out[j] (FP16)
    Shared 累加 local sum
  3. Pass 3: 正規化（除以 sum）
    每個 thread
    HBM 第三次讀 row_out[j]
    ALU 乘以 1 / row_sum
    去向
    HBM 覆寫 row_out[j]
⚠️ 同一 row 被讀/寫 HBM 3-4 次
正確做法：把整 row 載入 shared memory 或 register 一次，三 pass 都在那邊做，最後才寫回 HBM 一次。

③ quantize_fp16_to_int8 — FP16 → INT8 量化（2 個 kernel + 1 次 host 同步）

  1. Kernel A: abs_max_kernel — 找全 tensor 的 max|x|
    每 thread
    HBM 讀 input[idx] (FP16)
    ALU fabsf(__half2float(x))
    Block 內合併
    Shared tree reduction 取 block max
    HBM atomicMax 到 global scale_out
  2. Host 同步（超級慢的步驟）
    • cudaMemcpy GPU → CPU 拿 max（強制 GPU sync）
    • 在 CPU 算 scale = max / 127
    • cudaMemcpy CPU → GPU 寫回 scale
    • 這中斷整個 pipeline，GPU 停下來等 CPU
  3. Kernel B: quantize_kernel — 每個元素 × 1/scale → INT8
    每 thread
    HBM 又讀一次 input[idx]
    ALU round(x / scale)
    clamp
    去向
    HBM 寫 output[idx] (INT8)
⚠️ 三個問題
1. input 被讀了 2 次 HBM（abs_max 一次 + quantize 一次）
2. GPU ↔ CPU round-trip 拿 scale，強迫同步，整個 pipeline 停下來
3. 兩個 kernel 各自 launch，有 launch overhead

④ dequant_gelu_kernel — MLP 的 dequant + GELU（elementwise）

這個比較簡單，完全 elementwise，每 thread 一個元素。

來源
HBM input[idx]
4 bytes (INT32)
計算（register 內）
ALU x = (float)input × scale（dequant）
ALU inner = k0 × (x + k1 × x³)
SFU tanhf(inner)（特殊函數單元）
ALU g = 0.5 × x × (1 + tanh)
去向
HBM output[idx]
2 bytes (FP16)
這個 kernel 本身沒什麼可優化（已經 elementwise 最簡單形式）。
問題是它獨立存在：單獨從 HBM 讀一次、寫一次，完全是 memory-bound。
優化方向：fuse 進 GEMM epilogue，讓 GEMM 算完直接在 register 裡套 GELU，不用寫回 HBM 再讀。

fragment<matrix_a, 16, 16, 16, int8_t, row_major> a_frag[2]; // 2 個 A fragment fragment<matrix_b, 16, 16, 16, int8_t, row_major> b_frag[2]; // 2 個 B fragment fragment<accumulator, 16, 16, 16, int32_t> c_frag[2][2]; // 2×2 = 4 個 C fragment for (k = 0; k < K; k += 16) { load a_frag[0]: rows [row+0, row+16) load a_frag[1]: rows [row+16, row+32) load b_frag[0]: cols [col+0, col+16) load b_frag[1]: cols [col+16, col+32) ← 4 次 load，但接下來做 4 次 mma mma_sync(c_frag[0][0], a_frag[0], b_frag[0]); // a_frag[0] 用第 1 次 mma_sync(c_frag[0][1], a_frag[0], b_frag[1]); // a_frag[0] 用第 2 次 ← 重用！ mma_sync(c_frag[1][0], a_frag[1], b_frag[0]); // b_frag[0] 重用 mma_sync(c_frag[1][1], a_frag[1], b_frag[1]); } // 每個 fragment 被 2 個 mma 用到 → load/mma 比例從 2:1 變成 1:1

硬體行為：Arithmetic intensity 翻倍

v5.1 (16×16 output per warp): per k iter: 2 frag load (A, B) → 1 mma (16×16×16 = 4096 ops) load / ops = 2 / 4096 ≈ 0.0005 ← low intensity (wmma 在等 HBM load 的時間比較多) v6 (32×32 output per warp, 2×2 accumulators): per k iter: 4 frag load (A0, A1, B0, B1) → 4 mma (4 × 4096 = 16384 ops) load / ops = 4 / 16384 ≈ 0.00025 ← 2× better intensity (tensor core 更多時間真的在算) Fragment 重用視覺化: ┌───────────────────┐ │ warp (32 threads) │ 一個 warp 維護 4 個 c_frag └───────────────────┘ │ ┌─────────┴──────────┐ A_row0 A_row1 (b_frag0 共用給 A_row0/A_row1) │ │ ┌────┼────┐ ┌───┼────┐ c00 c01 c10 c11 ↑ ↑ ↑ ↑ B_c0 B_c1 B_c0 B_c1 (a_frag 共用給 B_c0/B_c1)
