6. Integration Risks to Watch (4/27–28)

When pulling Jonathan's and Sherry's WMMA implementations, Ashley should explicitly check:

Potential issue Why it matters for INT8
Fragment tile shape FP16 WMMA uses 16×16×16 tiles. INT8 WMMA can also use 16×16×16, but 8×8×32 and 32×8×16 are other options. If FP16 kernels hard-code tile layout, swapping to INT8 may require restructuring.
Shared-memory layout assumptions FP16 is 2 bytes, INT8 is 1 byte. Any smem index arithmetic assuming FP16 stride will break.
Accumulator dtype (FP32 vs INT32) Epilogue code (dequant, GELU, softmax) must handle INT32 accumulator for INT8 path vs FP32 for FP16 path.
Per-tensor vs per-row scales If teammates' kernels assume a single scalar input, INT8's scale-handling needs adaptation.
Softmax precision INT8 attention needs dequant → softmax (FP16) → quantize. FP16 kernel can do softmax inline in registers; INT8 may need a separate pass.
