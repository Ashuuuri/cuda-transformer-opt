INT8 整合現況說明

做了什麼、合不合理、接下來往哪裡走 — Heling / 2026-04-28

TL;DR

  1. 把 Sherry / Jonathan 的 FP16 kernel 裡的 fragment type 換成 INT8/INT32，input/output 都用 INT8
  2. Epilogue 做 dequant（INT32 × scale → float → GELU → FP16），中間 hidden 動態 requantize 成 INT8
  3. Scale 全部用 device pointer 傳進 kernel，移掉熱路徑上所有 cudaMemcpy
  4. 目前 MLP 比 FP16 慢 3.4×，bottleneck 是中間的 requantize pass，不是 GEMM 本身
  5. 這個版本是「直接型別替換」的起點，接下來可以針對 requantize 做特化

1. 整合方式：MLP

Sherry 的 FP16 kernel 原本的資料流：

FP16 xinput
→
WMMA GEMM1fp16×fp16→fp32
→
FP16 hidden+ GELU
→
WMMA GEMM2fp16×fp16→fp32
→
FP16 outoutput

我的 INT8 版本：

INT8 xinput
→
WMMA GEMM1int8×int8→int32
→
FP16 hiddendequant+GELU
→
requantize3 kernels
→
INT8 hiddendynamic scale
→
WMMA GEMM2int8×int8→int32
→
FP16 outdequant
→
requantize3 kernels
→
INT8 outoutput
紅框的 requantize 是目前的主要 overhead — 每次都要讀一遍整個 buffer 算 amax、再讀一遍寫 INT8，合計 6 個 kernel launch。

GEMM kernel 實際改了什麼

項目 Sherry FP16 Heling INT8 狀態

matrix_b fragment half, row_major int8_t, row_major 改
accumulator fragment float int32_t 改
smem type half int8_t 改
cp.async 16B = ? elements 8 elements 16 elements (loop ÷2) 改
epilogue acc → FP16 int32 acc × scale → GELU → FP16 改
tile shape / double-buffer 64×64, STAGE_K=32 64×64, STAGE_K=32（一樣） 不變
SMEM bank padding +8 halves = 16 bytes +16 int8 = 16 bytes（一樣） 不變
scale 傳入方式 不需要 const float* d_scale_A, d_scale_B（device ptr） 新增

2. 整合方式：Attention

Jonathan 的 attention 不直接用 INT8 WMMA 做 QK 計算，原因是他的 online softmax 直接讀 frag_qk.x[i]（register 裡的 float），INT32 accumulator 的 layout 未定義，硬改會出錯。所以 attention 的策略是：

INT8 Q/K/Vinput
→
load 時 dequantINT8→FP16 smem
→
FP16 smem Q/K/Vjonathan的原始邏輯
→
FP16 WMMA + softmax完全不動
→
epilogue quantfloat→INT8
→
INT8 outscale = scale_V

為什麼 output scale = scale_V

Attention output 是 softmax weights 對 V rows 的加權平均（convex combination）：

out = Σ wᵢ · Vᵢ,   其中 Σ wᵢ = 1,  wᵢ ≥ 0

所以 |out| ≤ max|V_real| = 127 × scale_V。output 用 scale_V 量化保證不 overflow，不需要額外計算 amax。

為什麼 MLP 還是很慢

cuBLAS 單個 INT8 GEMM = 0.086ms，FP16 兩個 GEMM = 0.083ms。 表示在這個 problem size（batch=2, seq=512），GEMM 本身就已經是 bandwidth-bound，INT8 的 2× compute 優勢顯示不出來。

加上兩次 requantize pass（各 3 個 kernel，讀/寫全 buffer），整個 MLP 從 0.083ms 變成 0.284ms。

Requantize 的成本：

動作Global memoryKernel launch
reduce_amax（第一次）讀 T×d_ff FP16 = 4MB1
finalize_scale（第一次）讀寫 4 bytes1
quantize（第一次）讀 4MB + 寫 2MB1
reduce_amax（第二次）讀 T×d_model FP16 = 1MB1
finalize_scale（第二次）讀寫 4 bytes1
quantize（第二次）讀 1MB + 寫 0.5MB1
合計~12.5MB 額外流量6 kernels

這 12.5MB 是在 GEMM 本身之外完全額外的 HBM 讀寫，FP16 版本完全沒有。

4. 這個起點合理嗎

合理的地方

  • 架構是正確的：WMMA fragment type 換成 int8/int32、epilogue dequant、scale 用 device pointer 傳遞，沒有 CPU sync 在熱路徑上
  • 可以作為對照組：現在的數字代表「直接型別替換，不做任何 INT8 特化」的 baseline，下一步的優化效果可以跟這個比
  • correctness 通過：attention max error 0.019、MLP max error 0.028，都在 atol=0.1 以內
  • sweep 可以跑：不同 seq_len / d_model 的數字跑出來可以看出哪個 size 有優勢

5. 接下來可以往哪裡做

A. 靜態 scale，消掉 requantize pass 省力

GEMM1 epilogue 直接寫 INT8，scale 用 scale_x × scale_W1 × d_model（保守靜態上界）。 完全不需要 reduce_amax kernel。 代價：精度比動態 scale 差，但省掉 6 個 kernel launch 和 12.5MB 的額外 HBM 流量。

B. Fuse quantize 進 WMMA epilogue 中等

GEMM1 epilogue 每個 thread 用 atomicMax 更新 global amax，最後一個小 kernel 算 scale， 然後再一個 pass 寫 INT8。省掉中間的 FP16 hidden buffer，減少一次完整的 buffer 讀寫。

C. 掃 larger batch size 省力

目前 batch=2 是 bandwidth-bound，GEMM 本身的 INT8 2× 優勢出不來。 sweep 跑到 seq_len=4096, d_model=2048 的大 size 才能看出 INT8 是否真的有 compute 優勢。

D. Attention 改用 INT8 WMMA for QK 困難

目前 attention 的 QK 計算用 FP16 WMMA，因為 online softmax 直接讀 frag_qk.x[i]。 改成 INT8 WMMA（INT32 accumulator）需要重寫 softmax 的 register 存取邏輯， INT32 fragment layout 未定義，風險高。

建議順序：先跑 sweep 拿到 C 的數字 → 如果大 size 下 INT8 有贏，再考慮 A 或 B 做進一步優化；如果還是沒贏，說明問題在 kernel 本身效率（tile size 等），再調 GEMM kernel 參數。
