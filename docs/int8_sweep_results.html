requantize 是什麼：GEMM 1 輸出的是 FP16，但 GEMM 2 需要 INT8 輸入。所以中間要跑 3 個 kernel 把 hidden 轉回 INT8：

步驟做什麼額外讀寫多少記憶體
① reduce_amax掃一遍 hidden，找最大值讀 全部 hidden（FP16）
② finalize_scale最大值 ÷ 127 = scale幾乎免費（1個數字）
③ quantize每個元素 ÷ scale，寫成 INT8讀 + 寫 全部 hidden

問題在：hidden 的大小 = batch × seq_len × d_ff，seq_len=4096, d_model=2048 時 hidden = 8192 × 8192 = 67M 個元素，光是讀寫這些就要花很多時間。而且 size 越大，這筆成本就越大，所以 speedup 一直維持在差不多的水平不改善。

為什麼 head_dim 越大越爛 — Shared Memory 的問題

我的 attention kernel 在 GPU 的 shared memory（smem）裡放 Q、K、V 的 tile， 方便 warp 快速存取。smem 的大小跟 head_dim 成正比：head_dim 越大，每個 block 佔的 smem 越多。

A100 每個 SM 有 164 KB 的 smem。如果一個 block 佔太多，同一個 SM 就只能跑少數幾個 block—— 這叫 低 occupancy，大量計算核心閒置，throughput 崩潰。

視覺化：每個 SM 能塞幾個 block

每個格子代表一個 block；灰色 = SM 空間。head_dim 越大，一個 block 佔的空間越多。

head_dim=256 時：一個 SM 只能跑 1 個 block，其他的算力全部空著等。這就是為什麼 speedup 只有 0.06×，比 FP16 慢 14 倍。
head_dim=64 時：一個 SM 可以跑 6 個 block，當一個 block 在等記憶體時，其他 block 繼續算。seq=4096 時 speedup 達到 0.91×，接近 FP16 的速度。
注意：標準 transformer（GPT-2、BERT 等）通常用 d_model=512, head_dim=64 這個設定，正好是我們最好的那個 case。head_dim=128/256 是更大的模型才會用到。

下一步可以做什麼

MLP：消掉 requantize pass
讓 GEMM 1 的 epilogue 直接輸出 INT8，不要繞過一個 FP16 buffer。 這樣省掉 6 個 kernel launch 和大量的 HBM 讀寫。 預期可以讓 MLP 從 0.24× 拉到接近 1× 甚至以上。
Attention：在標準設定下繼續優化
head_dim=64（d_model=512）的 0.91× 是合理的起點。 可以針對這個 case 做 tile size 調整，嘗試突破 1×。 head_dim=256 的問題是架構層面，短時間難以解決。
