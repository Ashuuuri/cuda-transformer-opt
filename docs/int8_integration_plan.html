0. 從零開始的觀念

看他們的 code 之前，這 6 個觀念要先弄清楚。我會用日常生活的比喻來解釋，不要被那些縮寫嚇到。

① Thread、Warp、Block 是什麼？

問：GPU 怎麼把工作分配給「很多個小工人」一起做？

GPU 分三層：
  • Thread：最小的工人，一個 thread 跑一份指令。
  • Warp：32 個 thread 一組，同步動作，像一個小隊。GPU 排程的真正單位是 warp，不是單一 thread。
  • Block：一群 warp（通常 1~8 個 warp），會跑在同一個 SM（GPU 上的「處理單位」，一個 GPU 有 100 多個 SM）。同個 block 的 thread 可以共用 shared memory。
比喻：把 GPU 想成連鎖速食店。
  • Thread = 一個店員
  • Warp = 一條櫃台（32 個店員一起服務一波客人）
  • Block = 一間分店（幾條櫃台，共用一個倉庫 = shared memory）
  • GPU = 整個連鎖（100 多間分店，每間獨立運作）
寫 CUDA kernel <<<grid, block>>>：grid 是「開幾間分店」，block 是「每間分店有幾個店員」。

② Tensor Core 是什麼？為什麼跟普通計算不一樣？

問：GPU 不是有 thread 在跑運算嗎？Tensor core 跟它差在哪？

GPU 的每個 SM 裡面除了普通的 ALU（CUDA core），還有 4 個專門做矩陣乘法的硬體，叫 tensor core。
一條 tensor core 指令一口氣完成 16×16×16 矩陣乘加 = 4096 次乘加。普通 CUDA core 一個 cycle 只能做 1 次乘加。
比喻：普通 CUDA core 像一個會煮飯的店員，一次煮一道菜。 Tensor core 像中央廚房的料理機，一按一次出 4096 份。
Transformer 95% 的計算量是矩陣乘法，所以這台「料理機」是吃飯的傢伙。不用它就是浪費 99% 的硬體。

A100 上的吞吐量：

  • FP16 tensor core 峰值 = 312 TFLOPS
  • INT8 tensor core 峰值 = 624 TOPS（FP16 的 2 倍）

③ WMMA 跟 Fragment 是什麼？

問：那要怎麼從 CUDA 程式碼裡面叫 tensor core？

用 NVIDIA 提供的一套 C++ API，叫 WMMA（Warp Matrix Multiply Accumulate）。一段 wmma 程式碼長這樣： 
wmma::fragment<matrix_a, 16, 16, 16, half, row_major> a_frag;
wmma::fragment<matrix_b, 16, 16, 16, half, row_major> b_frag;
wmma::fragment<accumulator, 16, 16, 16, float> c_frag;

wmma::load_matrix_sync(a_frag, A_ptr, ld);  // 載入 A 的 16×16 tile
wmma::load_matrix_sync(b_frag, B_ptr, ld);  // 載入 B 的 16×16 tile
wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);  // ⚡ 一次完成 4096 乘加
Fragment 是什麼？是「我這個 thread 在 wmma 操作中分到的那一小塊資料」。
WMMA 是 warp 級操作，一個 warp（32 thread）共同完成一個 16×16 的矩陣 tile = 256 個元素，每個 thread 拿 8 個。但你看不到 thread 拿的是哪 8 個 — 那是硬體內部決定的。
比喻：32 個店員合力做一個料理（16×16 矩陣），每人負責 8 個步驟。 料理機（tensor core）告訴他們各自做哪 8 個 — 你不用知道誰做了什麼，最後拼起來就是 256 步驟全做完。
關鍵點：正常用法你不會去看 fragment 內部。但 Jonathan 的 attention code 偏偏直接讀 frag.x[0..7]，這就是後面我們最該擔心的地方 — 因為他「假設」了 fragment 內部 layout，這個 layout 在 INT8 下是不是一樣，要實測才知道。

④ Shared Memory（smem）是什麼？

問：GPU 的記憶體不是只有 HBM 嗎？

GPU 有好幾層記憶體，速度差很多：
  • Register：每個 thread 自己的，最快（1 cycle），但很小（幾十個）
  • Shared memory（smem）：每個 SM 一塊（A100 有 164 KB），同 block 的所有 thread 共用，快（20 cycles）
  • L2 cache：整個 GPU 共用（A100 有 40 MB），中等（200 cycles），自動 cache HBM
  • HBM：主記憶體，大但慢（400 cycles）
比喻：
  • Register = 每個店員的口袋（拿東西最快）
  • Shared memory = 分店的小倉庫（店員之間共用，比走出店門快很多）
  • HBM = 城外的大倉庫（什麼都有但很遠）
典型優化：從大倉庫一次搬一批貨到分店倉庫，店員們從分店倉庫拿就好，少跑大倉庫的次數。這就是 tiling。

⑤ cp.async 是什麼？為什麼要用？

問：搬資料就搬資料，為什麼還要分「同步」跟「非同步」？

傳統做法：thread 自己讀 HBM 資料、寫進 smem。讀的 400 cycle 期間 thread 在發呆。
cp.async 是 A100 起新增的指令：thread 發出「請幫我搬這 16 bytes」的請求，搬運交給後台硬體做，thread 不用等，可以繼續做其他事，等需要那筆資料時再 wait。
比喻：
  • 傳統搬運：你叫店員自己跑大倉庫拿貨，他來回跑這一趟你的店就停擺了。
  • cp.async：你打電話給 Uber 司機（後台硬體）幫你送貨。司機去送的時候，店員可以繼續服務客人。司機快到時你才停下動作收貨。
這就是「computation hides memory latency」(計算蓋掉記憶體延遲)。

典型用法：double buffering

// stage 0：請後台搬下一個 tile 到 buffer[1]
cp.async(buffer[1], next_data);

// 同時，warp 用 buffer[0] 算當前的 tile
wmma::mma_sync(...);   // 用 buffer[0]

// 等下一個搬完，換 buffer，重複
cp.async.wait_group(0);
swap(buffer[0], buffer[1]);

⑥ Bank conflict 跟 smem swizzle 是什麼？

問：shared memory 不是已經夠快了嗎，為什麼還要做 swizzle？

Shared memory 內部分成 32 個 bank（小櫃子），每個 4 bytes 寬。 一個 warp（32 thread）一起讀的時候：
  • 32 個 thread 各讀「不同的 bank」 → 全速，1 個 cycle 完成
  • 32 個 thread 同時讀「同一個 bank」 → bank conflict，硬體把它排隊處理，最慘變 32 倍慢
比喻：shared memory 像一棟樓有 32 個編號小櫃子。
  • 32 個店員各拿一個櫃子 → 全速。
  • 32 個店員都搶同一個櫃子 → 一個一個排隊。
Swizzle = 故意把資料擺得「亂」一點，讓 32 個 thread 自然落在不同櫃子。 最簡單的方式是「每行多塞幾個 padding 位置」，把資料的位置錯開。Sherry 跟 Jonathan 都用這招（SMEM_PAD=8）。

⑦ Online Softmax 是什麼？

問：為什麼要叫「online」？普通 softmax 不行嗎？

普通 softmax 的步驟：
  1. 掃整行找最大值
  2. 每個值減去最大值，算 exp，加總
  3. 每個值除以總和
問題是 步驟 1 必須看完整行才能繼續。在 attention 裡，每一行有 512 個值，先寫到 HBM、再讀出來掃一次，記憶體成本高。

Online softmax 邊算邊維護兩個累加器（running_max, running_sum），每看到新一塊就更新。不用一次看完整行。
比喻：普通 softmax 像「先看完整本書再寫讀後感」。 Online softmax 像「邊看邊寫筆記，看到新內容就修改之前的判斷」。 結果一樣，但你不用先把書讀完才能動筆。
為什麼重要？有 online softmax，attention 的「Q × K^T → softmax → × V」三個步驟可以塞進同一個 kernel，中間結果都留在 register/smem，不用寫 HBM。這就是 FlashAttention 的核心想法。

2. MLP 換成 INT8 要做什麼

「換 INT8」聽起來簡單，但具體有哪些事要動？分成「保留」、「微調」、「重寫」三類。

面向 Δ FP16 版本 INT8 版本
Block 64×64、8 warps = 整個 layout 結構 完全不動 — tile 大小是「元素數」，跟 dtype 無關
cp.async 機制 = 後台搬資料 完全不動 — cp.async 是 byte-level 的，不挑 dtype
Workspace 暫存 cache = 避免 cudaMalloc 沿用同樣 pattern
Fragment dtype ≠ half + float accum 改成 int8_t + int32_t accum
cp.async 一次搬 16 bytes ~ 16 bytes = 8 個 half 16 bytes = 16 個 INT8，loop bound 要 ÷2
SMEM_PAD=8 ~ 8 halves = 16 bytes 偏移 8 INT8 = 8 bytes 偏移，避不開 bank conflict，要重算
GELU epilogue ≠ FP32 acc → GELU → 寫 FP16 INT32 acc → ×scale → FP32 → GELU → 量化 → 寫 INT8

INT8 版的矩陣視覺化（橘色=INT8、紅色=INT32 累加）

INT8 1 byte 整數 INT32 4 byte 整數（GEMM 累加用） FP16 2 byte 浮點（GELU/輸出用） FP32 4 byte 浮點（dequant 中間值）

3. Jonathan 的 Attention 在做什麼

Attention 的計算比 MLP 複雜：

out = softmax(Q @ K^T / √d) @ V
需要兩個矩陣乘法 + 中間一個 softmax。最大的麻煩是 softmax — 需要看整行才能算，但矩陣是 512×512，整行 512 個值塞不進 register。

先解釋：為什麼有 batch × heads = 16 個獨立計算

這是看 attention 之前要先理解的概念。「一次 attention forward」其實是 16 個獨立的小 attention 在跑。

原因：

  • Batch = 2：同時處理 2 句話（例如：「The cat sat」跟「A dog runs」）。兩句話獨立，不需要互相 attend。
  • Heads = 8：multi-head attention 的設計。每個 head 負責看不同類型的關係（例如 head 0 看主詞-動詞、head 1 看代名詞指誰...）。每個 head 用自己的 W_Q / W_K / W_V，產出自己的 Q/K/V，互相不影響。

所以同一次 forward 裡，2 句話 × 8 個 head = 16 個完全獨立的 attention 在算。每個用自己的 Q、K、V 算自己的 output。

問題 1：scores 矩陣超大

中間的 scores 是 512 × 512 = 26 萬個值。如果是 FP32，就是 1 MB。
塞進 shared memory（每個 SM 164 KB）已經很擠，更別說每行還要做 softmax（要看完整行才能 normalize）。

512×512 = 1 MB
太大塞不下

問題 2：傳統 softmax 要看「整行」才能算

Softmax 公式：

softmax(x_i) = exp(x_i - max(x)) / Σ exp(x_j - max(x))
                              ↑                ↑
                       要先掃整行找 max     再掃一次累加 sum

所以傳統做法要：①掃一次找 max → ②掃一次算 exp + sum → ③再掃一次 normalize。 三次掃 512 個值，記憶體成本高。

解法 1：Online Softmax — 邊算邊累加，不用看整行

聰明的做法：每看到新的一塊就 更新 running max 跟 running sum。看到一塊算一塊，不用等整行。

看到新一塊 [score_a, score_b, ...]:
  new_max = max(running_max, max(this_block))
  correction = exp(running_max - new_max)
  running_sum *= correction          ← 修正之前的累加
  running_sum += sum(exp(score - new_max))
  running_max = new_max
💡 這樣 QK^T → softmax → ×V 三步可以塞進一個 kernel，scores 不用全部存出來。這就是 FlashAttention 的核心。

解法 2：Q 沿 row 切成 32 一段 — 每個 block 負責 32 個 Q row

整個 Q 還是太大（512 row 全部處理太多），所以也切：

Q

Block i 負責算 output 的 row [i×32 .. i×32+31]。

一個 block 雖然只負責 32 個 Q row，但每個 Q row 都要對全部 512 個 K 算 attention：

K 也要切：KV tile 沿 K 滑動，每次 32 個

整個 K (512, 64) 是 32 KB，塞 smem 不夠舒服。所以 K 也切成 32 row 一段，每次只搬一段進 smem：

cp.async 雙 buffer：載入下一個 KV tile 跟算當前 tile 重疊

每個 KV tile 大小是 32 × 64 × 2 (half) = 4 KB（K 和 V 各一份）。雙 buffer 讓搬跟算 overlap：

時間 →

序列化：
  搬 KV[0] ▓▓ → 算 KV[0] ▒▒ → 搬 KV[1] ▓▓ → 算 KV[1] ▒▒ ...

雙 buffer cp.async：
  搬 KV[0] ▓▓
              ↓
              算 KV[0] ▒▒  ＋ 同時搬 KV[1] ▓▓
                                  ↓
                                  算 KV[1] ▒▒ ＋ 同時搬 KV[2] ▓▓

Block 內部：2 個 warp 各管 16 Q row

一個 block 有 32 Q row，配 2 個 warp（=64 thread）。每個 warp 負責 16 row，自己維護自己的 online softmax 狀態：

Warp 0
負責 Q row 0..15
register: rmax0, rsum0
不跟 warp 1 通訊
Warp 1
負責 Q row 16..31
register: rmax1, rsum1
不跟 warp 0 通訊
block 32 row 平分給 2 warp
💡 兩個 warp 完全獨立，不需要 __syncthreads，不需要 cross-warp reduction。但兩個 warp 共用同一份 KV tile（在 smem 裡）。

每個 KV tile 內，warp 在做的 6 步

每跑一個 KV tile (32 個 K)：

  1. wmma:  Q × K^T → 32×32 scores (FP32 register)
  2. ÷ √d  套縮放
  3. 算 row max  (warp shuffle，warp 內 reduction)
  4. online softmax 更新：
       new_max = max(rmax, lmax)
       correction = exp(rmax - new_max)
       frag_out *= correction         ← 修正之前累加的
       rsum *= correction
  5. exp(score - new_max) → softmax weight
       寫進 s_scores_h (smem)
       rsum += sum(weights)
  6. wmma:  weights × V → frag_out (繼續累加)

跑完 16 個 tile 後：
  out = frag_out × (1 / rsum)  → 寫 HBM
💡 Online softmax 讓步驟 1-6 全部塞進一個 kernel。中間結果 (scores, weights) 不用寫 HBM，全在 register / smem 流動。

總結：完整 hierarchy

整個 attention：16 個獨立 (batch, head) 同時跑
└─ 每個 (batch, head) 的 Q (512, 64) 切成 16 個 block，每 block 32 Q row
    └─ 一個 block 沿 K 跑 16 次（每次處理 32 K，cp.async 重疊搬與算）
        └─ 每次 KV tile，block 內 2 個 warp 各算自己 16 row 的 6 步
            └─ 每個 warp 用 wmma 算 16×16 sub-tile，online softmax 在 register 累加

5. 共通要注意的事

量化粒度（per-tensor / per-row / per-block）

粒度怎麼做適合 Sherry MLP？適合 Jonathan Attention？
Per-tensor 整個 tensor 一個 scale 可（加獨立 quantize kernel） 可（但要 global reduction）
Per-row 每個 output row 一個 scale 不行（block 沒涵蓋整 row） 可（warp 涵蓋自己的 row）
Per-block 每個 block tile 一個 scale 可 不太自然

Bank conflict 重算

shared memory 32 個 bank，每個 4 bytes。「跨幾個 bank」決定有沒有 conflict：

  • FP16 row 32 個元素 = 64 bytes → 跨 16 個 bank
  • INT8 row 32 個元素 = 32 bytes → 跨 8 個 bank（更密集，conflict 機率更高）
  • PAD=8: FP16 = 16 bytes，避開；INT8 = 8 bytes，沒避開

所以 INT8 應該用不同 PAD（例如 16 個元素 = 16 bytes，跟 FP16 的 byte 偏移一致）。

Scale 處理

FP16 kernel 都不接 scale。INT8 至少要：

  • MLP：scale_x, scale_W1, scale_W2
  • Attention：scale_Q, scale_K, scale_V
  • 另外用 device pointer 傳中間 scale（避免 CPU sync，沿用 v6 pattern）
